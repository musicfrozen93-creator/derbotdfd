# Deriv Market Condition Analyzer

A standalone Python service for an Ubuntu VPS. It watches Deriv's Synthetic Index digit
markets and checks whether the exact purchase conditions of your 10 DBot bots have recently had
a **statistically reliable edge over the real payout**. It sends Telegram messages only when a
bot × market combination **starts** or **stops** meeting every condition, and for critical
data or system faults.

> **What it is not.** It does not trade, buy, sell, log in to your Deriv account, run bots,
> change stakes or edit your XML files. It needs no Deriv token. A START message means that past
> data passed a strict set of tests. It is **not** a prediction of the next tick and **not** a
> guarantee of profit. Deriv's synthetic indices are generated by a random number generator.
> The expected steady state is that nothing qualifies and no START is ever sent.

## How it works

```
Deriv public WebSocket ──► collector ──► SQLite (WAL) ──► analyzer (every 60 s) ──► signal engine ──► Telegram
 active_symbols            live ticks     ticks, state     replays each bot's         START / STOP      outbox with
 contracts_for             + history      payouts, ...     XML conditions per         + confirmation    retries
 proposal (quotes only)    backfill                        market, statistics         + cooldown
```

1. **Discovery** (every 6 h): `active_symbols` + `contracts_for` list the synthetic indices that
   offer the digit contracts each bot needs. This builds a bot × market compatibility matrix
   (contract type, barrier range, tick duration).
2. **Collection**: one tick stream per market. On first start it downloads history (default
   400,000 ticks per market, about 4.6 days). After a reconnect it fills the gap. A gap audit
   runs every 10 minutes. Last digits are taken from the price formatted to the market's pip
   size (Decimal), so trailing zeros are kept.
3. **Payout**: quote-only `proposal` requests give the real payout. Break-even = stake / payout.
   No quote means INSUFFICIENT_DATA; a payout is never assumed.
4. **Analysis**: each leg of each bot is replayed on stored ticks with its own trigger,
   prediction and duration. Statuses:

   | Status | Meaning |
   |---|---|
   | `RUN_CANDIDATE` | Every test passed: ≥ 20,000 discovery trials, lower 95 % Wilson bound above break-even, survives Benjamini–Hochberg FDR, confirmed on a later out-of-sample block, recent 1k vs prior 4k stable, no abnormal losing runs, edge also holds at +1 tick settlement, beats the comparator (e.g. Delta's trigger vs unconditional), clean data for 30 min, contract listed |
   | `WAIT` | Enough clean data, but at least one RUN test not met (the normal state) |
   | `AVOID` | Win rate reliably below break-even, abnormal losing runs, digit distribution alarm, contract unavailable, or feed fault |
   | `INSUFFICIENT_DATA` | < 20,000 ticks, < 2,000 trigger events, or no payout quote |

   A multi-leg bot (Aria, Navix, Zony AI) is RUN_CANDIDATE only if every leg is.
5. **Signals**: `START` after 3 consecutive RUN_CANDIDATE evaluations; `STOP` after 3 consecutive
   failures, or **immediately** on a critical fault (contract withdrawn, feed stale or
   disconnected ≥ 120 s, market delisted). A brief data-quality dip freezes the counters instead
   of stopping. After a STOP the same combination cannot START again for 30 minutes. WAIT /
   AVOID / INSUFFICIENT changes are logged, **never** sent to Telegram. Every bot × market
   combination has its own state; one market's STOP never touches another.
6. **Persistence and restarts**: signal state and the notification outbox are in SQLite and
   change in one transaction, so a restart neither repeats a START nor loses a STOP. After a
   restart the confirmation counters start from zero. If the analyzer itself was down for
   ≥ 120 s (`signals.offline_stop_s`), every active signal gets a critical STOP, because it was
   not monitored. During the first 5 minutes after start (catch-up), data-fault STOPs are held
   back; contract faults are not.

## Install on the VPS (Ubuntu 22.04 / 24.04, 2 vCPU, 2 GB RAM)

Step-by-step commands, environment variables and the recommended dry-run stage are in
**`docs/DEPLOYMENT_UBUNTU_24.04.md`**. Short version:

```bash
scp -r deriv-market-analyzer user@your-vps:~/
```

```bash
ssh user@your-vps
```

```bash
cd ~/deriv-market-analyzer && chmod +x *.sh && sudo ./install.sh
```

The installer installs Python 3.11+, creates a `deriv-analyzer` system user, copies the app to
`/opt/deriv-market-analyzer`, builds a virtualenv, creates `.env` (mode 600), initialises the
database, validates the strategies, and installs and starts the `deriv-analyzer` systemd service
(enabled at boot, restarted automatically).

Then add your Telegram details:

```bash
sudo nano /opt/deriv-market-analyzer/.env
```

```
TELEGRAM_BOT_TOKEN=123456789:your-token-from-BotFather
TELEGRAM_CHAT_ID=your-chat-or-channel-id
ANALYZER_DRY_RUN=true
```

A fresh `.env` starts in **dry run** (`ANALYZER_DRY_RUN=true`): notifications are logged, not
sent. Set it to `false` after the Telegram test below works.

```bash
sudo /opt/deriv-market-analyzer/restart.sh
```

```bash
sudo -u deriv-analyzer /opt/deriv-market-analyzer/.venv/bin/python /opt/deriv-market-analyzer/scripts/test_telegram.py
```

This **Telegram test mode** sends a TEST START and a TEST STOP, both headed
"🧪 TEST MESSAGE — NOT A REAL SIGNAL". It never opens the database, so real signal states and the
notification queue are not touched (add `--print` to see the text without sending). To find your
chat id without typing the token anywhere, message your bot and run `scripts/telegram_chat_id.py`
the same way.

Without a token the service still runs and writes every notification to the log only.

## Deploy with Docker / Portainer CE

The project also ships as a one-service Docker stack for Portainer CE. Full guide:
**`docs/PORTAINER_DEPLOYMENT.md`**. Short version, on the VPS:

```bash
cd /opt/deriv-market-analyzer && sudo docker build -t deriv-market-analyzer:1.0.0 .
```

Then in Portainer go to **Stacks → Add stack → Web editor** and paste `docker-compose.yml`
(or use Repository mode with `docker-compose.repository.yml`). Set `TELEGRAM_BOT_TOKEN`,
`TELEGRAM_CHAT_ID` and `ANALYZER_DRY_RUN` as the stack's environment variables, then deploy.

| | |
|---|---|
| Container | non-root (uid 10001), read-only root filesystem, all capabilities dropped, no ports, no Docker socket |
| Data | volumes `deriv-analyzer-data` (`/app/data`: database, heartbeat, backups) and `deriv-analyzer-logs` (`/app/logs`), which survive container recreation |
| Default | dry run (`ANALYZER_DRY_RUN=true`) |
| Health | `scripts/healthcheck.py` reads the heartbeat; Portainer shows *healthy* / *unhealthy* |
| Backup / restore | `docker exec deriv-analyzer python scripts/backup_db.py`; `scripts/restore_db.py` |

The Docker image has not been built and the stack has not been deployed yet: no Docker engine
was available when these files were prepared. The guide lists the checks to run first.

## Operating it

| Command | What it does |
|---|---|
| `sudo ./start.sh` / `sudo ./stop.sh` / `sudo ./restart.sh` | systemd start / stop / restart |
| `sudo ./status.sh` | service state + heartbeat + current statuses per bot and market |
| `./logs.sh` | follow `logs/analyzer.log` |
| `.venv/bin/python scripts/report.py --matrix` | compatibility matrix |
| `.venv/bin/python scripts/report.py --bot delta` | detail for one bot (also `--symbol R_10`) |
| `.venv/bin/python scripts/live_api_check.py` | live Deriv API check (read-only) |
| `.venv/bin/python -m app.main --validate` | load config and strategies, print the inventory |
| `.venv/bin/python -m app.main --dry-run` | run in the foreground; notifications are logged, not sent |

Logs rotate at 10 MB × 10 files. Ticks older than 30 days are pruned. Expect about 1 hour of
history download on first start. Expect the database to reach about 1–1.5 GB after 30 days
with about 20 markets (measured: 16 MB per 460,000 ticks). Back it up with
`scripts/backup_db.py`, which takes a consistent copy while the service runs and keeps the
newest 3. Each evaluation cycle is logged at INFO (`event=evaluation_cycle`).

## Configuration

All settings are in `config.yaml`, with comments. Secrets are only in `.env`:
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, optional `ANALYZER_CONFIG` and `ANALYZER_DRY_RUN`.
The token is never logged; any token-shaped string is redacted from the logs. Common changes:

* `strategies.enabled`: `[all]` (default: all 10 bots) or a list such as `[aria, aria_v2, navix]`.
* `discovery.max_symbols` (default 40, above the 19–20 compatible markets Deriv lists, so every
  compatible market is monitored), `discovery.priority_symbols`, `discovery.exclude_symbols`.
* `analysis.*`: sample-size gates and test levels. **Loosening them produces noise signals.**
* `signals.*`: confirmation cycles, cooldown, startup grace.
* `telegram.daily_summary: true`: one summary a day at `daily_summary_time` (Asia/Colombo).

## Telegram messages

Only four kinds of message are sent:

* 🟢 **START SIGNAL**: bot, market, contract, sample sizes, win rate with 95 % CI, break-even,
  out-of-sample result, data quality, and losing-streak risk for that bot's own stake ladder.
* 🔴 **STOP SIGNAL**: why the combination no longer qualifies.
* ⚠️ **CRITICAL**: feed or connection down, or a system error, naming which active combinations
  are affected. Followed by ✅ **RECOVERED**.
* Optional daily summary.

Times are shown in Asia/Colombo with UTC alongside.

```bash
pip install -r requirements-dev.txt
```

```bash
python -m pytest -q
```

The 170+ tests use mocked Deriv and Telegram APIs (a local WebSocket server for reconnects). They
cover digit extraction with trailing zeros, the compatibility matrix, market discovery (all
compatible markets, added / delisted markets, failed `contracts_for`), strategy triggers and
sequences, the statistics, validation gates, **every START/STOP state transition**
(`tests/test_signal_transitions.py`, including restarts, downtime, feed failure end to end and
the outbox), duplicate prevention, independent combinations, reconnect and backfill, gap
detection, payout handling, Telegram test mode, message formatting and token redaction.

## Limitations and honest expectations

* Deriv states the synthetic indices are driven by a cryptographically secure RNG. On such data,
  a conditional win rate above break-even is not expected. In the live tests every combination
  came out WAIT, AVOID or INSUFFICIENT_DATA (19 markets × 10 bots in the production-config run). Treat any START with suspicion and confirm it on a
  demo account.
* Even a correct START describes the past. It does not change the probability of the next tick.
* Martingale-style ladders (most of these bots) can lose far more than they win. The START
  message shows the streak cost from the bot's own XML settings for that reason.
* Tick alignment, the Navix timeout ordering and Zony AI's overflow behaviour are assumptions
  that need a few demo-account trades to confirm. See `docs/STRATEGY_INVENTORY.md`.
* The same hypotheses are re-tested every minute on mostly overlapping data. FDR control,
  the out-of-sample block, the latency check and the stability check make a false START rare,
  but over months of running one remains possible.
* If the analyzer itself is down for 120 s or more, active signals get a STOP on restart and
  need the full confirmation again (plus the 30-minute cooldown) before a new START.
* A Telegram message that still fails after 20 attempts (about 11 hours of retries) is marked
  failed and the queue moves on; it stays visible in `scripts/report.py`.
* CPU: about 11 s per evaluation cycle (50 s every 30 minutes with the streak simulation) for
  20 markets × 400k ticks on a 3.2 GHz desktop core; a VPS core may be slower. Watch for
  `evaluation_slow` in the log during the dry run.
* Ubuntu installation and real Telegram delivery have not been tested yet; see
  `docs/FINAL_AUDIT_REPORT.md`. The Docker image build, `docker compose`, the Portainer stack
  and SIGTERM handling on Linux have not been run either; only the unit tests and a Windows
  simulation of the container lifecycle have.
* Telegram or VPS outages can delay a message. Notifications are queued and retried in order,
  and a heartbeat file plus a silence alert make gaps visible.
