# Deriv Market Condition Analyzer

A standalone Python service for an Ubuntu VPS. It watches Deriv's Continuous Indices and
evaluates each of your 10 DBot bots on each market **the way the bot's own XML trades**, in
five separate parts:

| Part | Question | Statuses |
|---|---|---|
| A. Entry | Did the bot's own entry rule (XML `before_purchase`) fire on the ticks of the last check? | PASS / FAIL / NOT_CHECKED |
| B. Statistics | How did the bot's own contracts, bought on its own entry ticks and settled on the right tick, do over the long window? | PASS / FAIL / NOT_CHECKED / UNAVAILABLE |
| C. Economics | Live Deriv quote at the bot's real stake → net win, net loss, break-even, expected value | POSITIVE / NEGATIVE / INCONCLUSIVE / NOT_CHECKED / UNKNOWN |
| D. Risk | Can the bot's own recovery (martingale) sequence be executed: payout cap, minimum stake, bankroll? | SAFE / UNSAFE / BLOCKED / UNKNOWN |
| E. Decision | START only when every required part passes; STOP at once when risk is UNSAFE / BLOCKED | RUN_CANDIDATE / WAIT / AVOID / INSUFFICIENT_DATA |

It sends Telegram messages only when a bot × market combination **starts** or **stops**
qualifying, and for critical data or system faults. The old "every winning digit > 10 % of the
last 500 ticks" rule is still computed and shown, labelled **informational**; it gates nothing.

> **What it is not.** It does not trade, buy, sell, log in to your Deriv account, run bots,
> change stakes or edit your XML files. It needs no Deriv token (quotes come from the public,
> read-only `proposal` call; nothing is bought). A START is **not** a prediction of the next tick
> and **not** a guarantee of profit. Deriv's synthetic indices are generated by a random number
> generator and every digit payout includes Deriv's commission, so with fair digits the expected
> value is negative and the default configuration sends **no START** (see "Honest expectations").

## How it works

```
Deriv public WebSocket ──► collector ──► SQLite (WAL) ──► evaluator (every 60 s) ──► signal engine ──► Telegram
 active_symbols            live ticks     ticks, quotes,   entry / statistics /       START / STOP      outbox with
 contracts_for             + history      evaluations,     economics / risk per       + confirmation    retries
 proposal (quotes) ──► quote service      history          bot x market               + cooldown, limit
```

1. **Discovery** (every 6 h): `active_symbols` lists every market; the **market filter** keeps
   only Deriv's *Continuous Indices* (API submarket `random_index`: R_10, R_25, R_50, R_75,
   R_100 and any new one Deriv adds) plus the two 1-second indices the bot XML files trade
   (1HZ10V, 1HZ50V). Jump, Crash/Boom, Range Break, Daily Reset, Step, Forex/Commodities Basket
   and all non-synthetic markets are dropped here, before anything else sees them.
   `contracts_for` then checks which kept markets offer the digit contracts each bot needs. This
   builds a bot × market compatibility matrix (contract type, barrier range, tick duration).
   Live on 2026-11-17: 7 markets, 70 bot × market combinations
   (`python scripts/list_markets.py` shows the current split).
2. **Collection**: one tick stream per market. On first start it downloads history (default
   400,000 ticks per market, about 4.6 days). After a reconnect it fills the gap. A gap audit
   runs every 10 minutes. Last digits are taken from the price formatted to the market's pip
   size (Decimal), so trailing zeros are kept.
3. **Quotes** (`app/economics/quotes.py`): a background service asks Deriv's public `proposal`
   call for the exact stakes each bot uses — the first stake of every contract and every stake of
   its losing streak — at most 30 per minute, refreshed every 6 h. Refusals are kept too: their
   message states the platform limits ("Minimum stake of 0.35 and maximum payout of 1000.00"),
   recorded as *observed on the public, unauthenticated quote endpoint*.
4. **Bot-specific evaluation** (`app/strategy_model/`), every 60 s, for every bot × market:
   * the strategy model (`bots.py`) reproduces each XML: entry rule, contracts and predictions,
     durations, the stake ladder of a losing streak (rounded like DBot's `toFixed(2)`), take
     profit, stop loss, stop and reset conditions. It is cross-checked against
     `strategies/*.yaml` at start-up and the service refuses to start on a mismatch;
   * **A entry**: the bot's own `before_purchase` rule — every tick (Aria, Aria V2, Voltrix,
     Predator v2, Zony AI), last digit 1 (Delta), last digit 4 / 6 (Navix base / recovery), last
     digit in {0, 3, 6, 9} (Pulse2), the Crysis 7-digit pattern, price ≥ SMA(8) (Predator,
     same floating-point order as the XML);
   * **B statistics**: the bot's contracts on its own entry ticks, bought on the next tick and
     settled after the contract's duration, over the last 100,000 ticks (long window) — never a
     contract that spans a feed gap, never an unsettled one. FAIL only if the 99 % Wilson
     interval lies entirely below the fair probability; fewer than 100 settled entries is
     NOT_CHECKED. Overlapping windows are not treated as independent: one interval on one window;
   * **C economics**: net win = payout − stake, net loss = stake, break-even = stake / payout,
     EV = p × net win − (1 − p) × net loss with one-sided 99 % bounds: POSITIVE only if EV > 0 even
     at the lower bound. No fresh quote for the exact stake → UNKNOWN (never a pass). The payout
     formula found in the audit is only used to cross-check quotes (`report.py --quotes`);
   * **D risk** (`app/risk/engine.py`): every trade of the bot's losing streak (from a fresh run
     and from just below its take-profit) is checked against Deriv's answer for that exact stake
     and against the configured bankroll. SAFE = every trade the bot can need before its own
     stop rule is accepted and affordable; UNSAFE = a later trade is refused (payout above the
     maximum) or unaffordable — DBot then stops with the loss so far, it cannot continue
     (`ContractBuyValidationError` / `InsufficientBalance` are unrecoverable in DBot); BLOCKED =
     the very next trade is refused; UNKNOWN = a quote is missing or no bankroll is configured;
   * **E decision**: `RUN_CANDIDATE` only if every gate in `evaluation.start_requires` passes
     (default all four; `risk` cannot be removed) and the live feed is current.

   | Status | Meaning |
   |---|---|
   | `RUN_CANDIDATE` | Every required gate passes, live feed OK |
   | `WAIT` | A required gate does not pass (or all pass but the live feed is late: counters frozen) |
   | `AVOID` | Critical: contract no longer offered, live feed down, or risk UNSAFE / BLOCKED |
   | `INSUFFICIENT_DATA` | Fewer than 500 ticks stored for the market yet |
   | `PASS` / `FAIL` | A check ran and passed / failed |
   | `NOT_CHECKED` | Not enough data to run the check reliably — never counted as a pass |
   | `UNAVAILABLE` | The contract is not offered on this market |
   | `UNKNOWN` | No valid quote / no bankroll: payout or risk cannot be judged — never a pass |
   | `SAFE` / `UNSAFE` / `BLOCKED` | Risk, see D above |

   Every cycle is written in one transaction: `evaluations` (summary JSON), `strategy_evaluations`
   and `leg_evaluations` (latest), `evaluation_history` (append-only, one row whenever a verdict
   changes) and `contract_results` (the legacy digit rule, informational).
5. **Signals**: `START` after 3 consecutive passing checks; `STOP` after 3 consecutive failing
   checks, or **immediately** on a critical fault (contract withdrawn, feed stale or
   disconnected ≥ 120 s, market delisted, **risk UNSAFE / BLOCKED**). A late live feed freezes
   the counters instead of stopping. After a STOP the same combination cannot START again for 30 minutes. WAIT /
   AVOID / INSUFFICIENT changes are logged, **never** sent to Telegram. Every bot × market
   combination has its own state; one market's STOP never touches another.
6. **Persistence and restarts**: signal state and the notification outbox are in SQLite and
   change in one transaction, so a restart neither repeats a START nor loses a STOP. After a
   restart the confirmation counters start from zero. If the analyzer itself was down for
   ≥ 120 s (`signals.offline_stop_s`), every active signal gets a critical STOP, because it was
   not monitored. During the first 5 minutes after start (catch-up), data-fault STOPs are held
   back; contract and risk faults are not.

## Install on the VPS (Ubuntu 22.04 / 24.04, 2 vCPU, 2 GB RAM)

Step-by-step commands, environment variables and the recommended dry-run stage are in
**`docs/DEPLOYMENT_UBUNTU_24.04.md`**. Short version:

```bash
scp -r deriv-market-analyzer user@your-vps:~/
```

```bash
ssh user@your-vps
```

```bash
cd ~/deriv-market-analyzer && chmod +x *.sh && sudo ./install.sh
```

The installer installs Python 3.11+, creates a `deriv-analyzer` system user, copies the app to
`/opt/deriv-market-analyzer`, builds a virtualenv, creates `.env` (mode 600), initialises the
database, validates the strategies, and installs and starts the `deriv-analyzer` systemd service
(enabled at boot, restarted automatically).

Then add your Telegram details:

```bash
sudo nano /opt/deriv-market-analyzer/.env
```

```
TELEGRAM_BOT_TOKEN=123456789:your-token-from-BotFather
TELEGRAM_CHAT_ID=your-chat-or-channel-id
ANALYZER_DRY_RUN=true
```

A fresh `.env` starts in **dry run** (`ANALYZER_DRY_RUN=true`): notifications are logged, not
sent. Set it to `false` after the Telegram test below works.

```bash
sudo /opt/deriv-market-analyzer/restart.sh
```

```bash
sudo -u deriv-analyzer /opt/deriv-market-analyzer/.venv/bin/python /opt/deriv-market-analyzer/scripts/test_telegram.py
```

This **Telegram test mode** sends a TEST START and a TEST STOP, both headed
"🧪 TEST MESSAGE — NOT A REAL SIGNAL". It never opens the database, so real signal states and the
notification queue are not touched (add `--print` to see the text without sending). To find your
chat id without typing the token anywhere, message your bot and run `scripts/telegram_chat_id.py`
the same way.

Without a token the service still runs and writes every notification to the log only.

## Deploy with Docker / Portainer CE

The project also ships as a one-service Docker stack for Portainer CE. Full guide:
**`docs/PORTAINER_DEPLOYMENT.md`**. Short version, on the VPS:

```bash
cd /opt/deriv-market-analyzer && sudo docker build -t deriv-market-analyzer:1.0.0 .
```

Then in Portainer go to **Stacks → Add stack → Web editor** and paste `docker-compose.yml`
(or use Repository mode with `docker-compose.repository.yml`). Set `TELEGRAM_BOT_TOKEN`,
`TELEGRAM_CHAT_ID` and `ANALYZER_DRY_RUN` as the stack's environment variables, then deploy.

| | |
|---|---|
| Container | non-root (uid 10001), read-only root filesystem, all capabilities dropped, no ports, no Docker socket |
| Data | volumes `deriv-analyzer-data` (`/app/data`: database, heartbeat, backups) and `deriv-analyzer-logs` (`/app/logs`), which survive container recreation |
| Default | dry run (`ANALYZER_DRY_RUN=true`) |
| Health | `scripts/healthcheck.py` reads the heartbeat (fresh heartbeat, Deriv connection, and an evaluation cycle saved within the last 10 min); Portainer shows *healthy* / *unhealthy* |
| Backup / restore | `docker exec deriv-analyzer python scripts/backup_db.py`; `scripts/restore_db.py` |

The Docker image has not been built and the stack has not been deployed yet: no Docker engine
was available when these files were prepared. The guide lists the checks to run first.

## Operating it

| Command | What it does |
|---|---|
| `sudo ./start.sh` / `sudo ./stop.sh` / `sudo ./restart.sh` | systemd start / stop / restart |
| `sudo ./status.sh` | service state + heartbeat + current statuses per bot and market |
| `./logs.sh` | follow `logs/analyzer.log` |
| `.venv/bin/python scripts/report.py --matrix` | compatibility matrix |
| `.venv/bin/python scripts/report.py --bot delta` | detail for one bot (also `--symbol R_10`): every check, legs, payout, EV, risk ladder |
| `.venv/bin/python scripts/report.py --quotes` | stored Deriv quotes, observed platform limits, payout-formula cross-check |
| `.venv/bin/python scripts/report.py --history` | recent verdict changes (`evaluation_history`) |
| `.venv/bin/python scripts/migrate.py --status` | schema version; `--to 3` rolls the v4 tables back (history kept) |
| `.venv/bin/python scripts/replay_strategy_model.py --ticks DIR ...` | offline replay of stored ticks through the evaluator |
| `.venv/bin/python scripts/live_api_check.py` | live Deriv API check (read-only) |
| `.venv/bin/python -m app.main --validate` | load config and strategies, print the inventory |
| `.venv/bin/python -m app.main --dry-run` | run in the foreground; notifications are logged, not sent |

Logs rotate at 10 MB × 10 files. Ticks older than 30 days are pruned. Expect about 1 hour of
history download on first start. Expect the database to reach about 0.4–0.5 GB after 30 days
with the 7 monitored markets (about 4.5 ticks/s in total; measured: 16 MB per 460,000 ticks). Back it up with
`scripts/backup_db.py`, which takes a consistent copy while the service runs and keeps the
newest 3. Each evaluation cycle is logged at INFO (`event=evaluation_cycle`).

## Configuration

All settings are in `config.yaml`, with comments. Secrets are only in `.env`:
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, optional `ANALYZER_CONFIG` and `ANALYZER_DRY_RUN`.
The token is never logged; any token-shaped string is redacted from the logs. Common changes:

* `strategies.enabled`: `[all]` (default: all 10 bots) or a list such as `[aria, aria_v2, navix]`.
* `discovery.include_submarkets` (default `[random_index]` = Continuous Indices only) and
  `discovery.one_second_symbols` (default `[1HZ10V, 1HZ50V]`): the market filter. Categories come
  from Deriv's `active_symbols` reply, so a newly listed Continuous Index is picked up
  automatically; a new 1-second index is not, until you add it here.
* `discovery.max_symbols` (default 40, far above the 7 markets the filter keeps),
  `discovery.priority_symbols`, `discovery.exclude_symbols`.
* `risk.bankroll_usd` (default `null`): the balance available to a bot. **While it is `null`
  every risk check is UNKNOWN and no START is sent.** `risk.bankroll_per_bot` overrides it per bot,
  `risk.base_stakes` tells the analyzer if you changed a bot's Base Stake in DBot, and
  `risk.max_payout_override` / `risk.min_stake_override` replace the limits seen on public quotes
  with your account's verified ones.
* `evaluation.*`: `long_window_ticks` (100,000), `confidence` (0.99), `min_outcomes` (100),
  `entry_gap_ticks` (1), `start_requires` (default `[entry, statistics, economics, risk]`;
  `risk` is mandatory).
* `economics.*`: `refresh_hours` (6), `max_quote_age_hours` (24), `retry_seconds` (60), `currency`.
* `signal_rule.*`: `window_ticks` (500) is the recent window and the minimum data before a
  combination is evaluated; `threshold_pct` / `contracts` / `mode` only affect the legacy digit
  rule, which is informational.
* `analysis.interval_s`: how often every combination is evaluated (60 s).
* `signals.*`: confirmation cycles, cooldown, startup grace, and the per-bot START limit:
  `max_starts_per_bot` (default 5) START signals per bot, all markets together, in any rolling
  `start_limit_window_hours` (default 12). These two keys are optional (the defaults apply when
  they are absent); `max_starts_per_bot: 0` switches the limit off.

### Per-bot START limit

* Counted per bot over all markets, in a **rolling** window (not a calendar day): a START at
  10:00 stops counting at 22:00:00.
* Only STARTs that were actually issued count. They are written to the `signal_start_ledger`
  table in the same SQLite transaction as the START itself (primary key bot + market + time, so a
  START is never counted twice, and a START whose transaction fails is not counted and not sent).
* At the limit, a START that is otherwise due (3 consecutive passes, out of cooldown) is not sent.
  The combination's status becomes `SIGNAL_LIMIT_REACHED`, logged once (`event=signal_limit_reached`
  with the time the next slot frees) and stored once in `signal_events`. No Telegram message is sent
  for it. If the combination is still passing when an older START leaves the window, it STARTs then;
  if it stops passing, it needs 3 fresh consecutive passes again.
* **STOP is never limited**, and a STOP does not free a slot.
* If the ledger cannot be read or written, the START is not sent (fail closed); STOPs in the same
  cycle still run.
* Restarts do not reset it (the ledger is in the database). Upgrading a database from schema 2
  copies the STARTs already in `signal_events` into the ledger.
* **Dry-run** only changes delivery: START / STOP are decided and stored exactly as in live mode
  and the messages are marked `skipped`. Dry-run STARTs therefore use up the bot's limit **in that
  database**. Use a separate database for a dry-run, or expect up to 12 hours of carried-over
  STARTs when switching the same database from dry-run to live.
* `telegram.daily_summary: true`: one summary a day at `daily_summary_time` (Asia/Colombo).

## Telegram messages

Only four kinds of message are sent:

* 🟢 **START SIGNAL**: bot, market and symbol; **every contract from the XML** (type,
  prediction, duration, winning digits, when the bot uses it); the entry-condition status; the
  bot's own contract statistics with the 99 % interval; the quoted payout (net win, net loss,
  break-even); the expected value per trade with its range; all four checks side by side; the
  risk status with the next trade, the next stake after a loss, the longest losing streak before
  the bot stops, what that streak can lose and the bankroll it needs; the reason for START; and
  a plain statement that it is not a prediction that the bot will win.
* 🔴 **STOP SIGNAL**: the exact reason, every check that is not passing (entry or contract
  condition), the payout issue and the risk issue if any, and whether the 30-minute cooldown
  applies (until when). The cooldown and the START limit never delay a STOP.

Example STOP (real formatter output; Predator on R_50 with quotes from the validated payout
formula; the ANALYZER_STRATEGY_ALIGNMENT evidence folder has a START example too):

```
🔴 STOP SIGNAL (critical)

Bot: Predator
Market: Volatility 50 Index
Symbol: R_50

Reason for STOP: risk UNSAFE: trade 7 of a losing streak (DIGITOVER 3 1t at 729.00) is refused: payout 1,191.18 above the maximum payout 1,000.00. DBot stops after 6 losses at -364.00.
Checks not passing:
• Payout / expected value: INCONCLUSIVE — DIGITOVER 3 1t: win rate 59.37% (57.31% - 61.40%) straddles break-even 61.35%
• Risk: UNSAFE — trade 7 of a losing streak (DIGITOVER 3 1t at 729.00) is refused: …
Payout issue: DIGITOVER 3 1t: payout 1.63 for 1.00, break-even 61.35%, expected value INCONCLUSIVE
Risk issue: UNSAFE — …

Cooldown: applies — no new START for Predator on R_50 before 2026-11-21 00:40 (Asia/Colombo), 30 min, and then only after 3 consecutive passing checks. The cooldown and the START limit never delay a STOP.

ACTION: Stop running Predator on R_50.
```
* ⚠️ **CRITICAL**: feed or connection down, or a system error, naming which active combinations
  are affected. Followed by ✅ **RECOVERED**.
* Optional daily summary.

Times are shown in Asia/Colombo with UTC alongside.

## Limitations and honest expectations

* **With the default configuration no START is sent.** Every Deriv digit payout includes a
  commission (break-even above the fair probability), so with fair digits the expected value is
  negative and the economics check is never POSITIVE; on top of that `risk.bankroll_usd` is
  `null`, so risk stays UNKNOWN. In the 7-day replay of stored Deriv ticks the analyzer issued 0
  STARTs (the old digit rule issued 190). This is the intended, honest result, not a fault.
* Five bots (Predator, Predator v2, Navix, Pulse2, Crysis) are **UNSAFE at their default
  stakes**: their recovery sequence needs a stake whose payout is above the $1,000 maximum seen
  on public quotes, which Deriv refuses, and DBot stops with the loss so far. Their combinations
  are AVOID (critical) as soon as the quotes are in. If your account's maximum payout differs,
  set `risk.max_payout_override` only after verifying it on that account.
* The analyzer cannot see the running bot, so the **current recovery level is unknown**: the
  risk check always walks the streak from a fresh run (and from just below the take-profit).
  Entry is checked for the bot's fresh-run contract; a recovery-mode entry rule (Navix last digit
  6) is shown, not checked separately.
* Statistics use one long window (100,000 ticks) per check. Consecutive checks overlap almost
  entirely and are not independent, and testing 70 combinations every minute will produce some
  chance passes at the 99 % level; that is why economics (with its own lower bound) and risk are
  also required.
* The payout formula found in the audit (commission = max(1.2 % of payout, 0.02)) is used only to
  cross-check live quotes; the economics check always uses the live quote for the exact stake.
  The $1,000 maximum payout and 0.35 minimum stake are those stated by Deriv's own refusals on the
  public, unauthenticated endpoint; a real account can differ.
* Tick alignment (entry on the tick after the trigger), the Navix timeout ordering and Zony AI's
  overflow behaviour come from the DBot source and the audit, not from demo-account trades. See
  `docs/STRATEGY_INVENTORY.md`.
* The legacy 10 % digit rule is still stored and shown but gates nothing; past digit frequencies
  do not change the next digit.
* If the analyzer itself is down for 120 s or more, active signals get a STOP on restart and
  need the full confirmation again (plus the 30-minute cooldown) before a new START.
* A Telegram message that still fails after 20 attempts (about 11 hours of retries) is marked
  failed and the queue moves on; it stays visible in `scripts/report.py`.
* CPU / memory: an evaluation cycle replays every bot's entry rule and settlement over 7 ×
  100,000 ticks (numpy) and walks 10 losing-streak ladders per market; in the 7-day replay a full
  cycle of 70 combinations took 0.33 s on average and 0.63 s at most (Windows desktop CPU; a small
  VPS will be slower but far below the 60 s interval). The collector downloads 400,000 ticks of
  history per market on first start (`collection.bootstrap_target_ticks`); the evaluation needs
  the newest 100,000.
* Ubuntu installation and real Telegram delivery have not been tested yet; see
  `docs/FINAL_AUDIT_REPORT.md`. The Docker image build, `docker compose`, the Portainer stack
  and SIGTERM handling on Linux have not been run either; only the unit tests and a Windows
  simulation of the container lifecycle have.
* Telegram or VPS outages can delay a message. Notifications are queued and retried in order,
  and a heartbeat file plus a silence alert make gaps visible.
